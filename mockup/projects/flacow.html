#Flacow

La mejor aplicación para registrar tu progreso en el gimnasio y lograr tus objetivos de fuerza. Un side-project nacido de una frustración personal: ningún tracker que probé hablaba el lenguaje del entrenamiento progresivo.

##Overview

Flacow es una aplicación web full-stack para registrar tus entrenamientos. Querías ver si esa serie de press banca de hoy fue mejor que la de hace 6 semanas — pues lo ves de un vistazo, en una gráfica, sin abrir cinco pestañas ni rascar un Excel.

Construido como side-project, vive en producción en flacow.bfmu.dev y usa una arquitectura monorepo con frontend en React + MaterialUI y backend en NestJS.

##Contexto y problema

Llevo varios años entrenando con foco en progresión de carga. La rutina pide saber cuánto levantaste la sesión anterior, en cuántas series, con qué RPE. Probé un par de apps populares y todas fallaban en lo mismo:

  • UX pensada para casual fitness, no para fuerza
  • Imposible ver tendencias por ejercicio sin pagar premium
  • Captura de series lenta — 6 taps para registrar un set
Si una herramienta hace fricción justo en el momento en que la necesitás, dejás de usarla. Y un tracker que no usás no sirve.

##Stack técnico

React 18 frontend
SPA con Vite + React Router. Usé hooks custom para sincronizar estado de sesión activa.
MaterialUI UI kit
Theme custom para evitar el look genérico de MUI. Componentes pesados reescritos.
NestJS backend
API REST modular. Guards de auth, pipes de validación, separación controller/service/repo.
PostgreSQL db
Schema con índices compuestos sobre (user_id, exercise_id, date) para queries de tendencia rápidas.
JWT auth
Access + refresh tokens con rotación. Sesión persiste 30 días en mobile.
Docker + Nginx deploy
docker-compose en VPS modesto. Nginx como reverse proxy con SSL via Certbot.

##Decisiones de arquitectura

###Monorepo con apps separadas

Frontend y backend viven en el mismo repo pero como paquetes independientes. Comparten un paquete shared/ con tipos TypeScript de los DTOs — un cambio en el contrato compila en ambos lados o explota el build.

###Modelo de datos por sesión

En vez de modelar 'sets' sueltos, todo cuelga de una WorkoutSession. Esto hizo que las queries de progreso sean joins rápidos en lugar de subqueries de agregación cara.

typescript · entities/workout-session.entity.ts 
@Entity()
export class WorkoutSession {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @ManyToOne(() => User, { eager: false })
  @Index()
  user: User;

  @OneToMany(() => ExerciseLog, log => log.session, {
    cascade: true,
  })
  logs: ExerciseLog[];

  @CreateDateColumn()
  startedAt: Date;

  @Column({ type: 'jsonb', nullable: true })
  notes: SessionNotes;
}

###Auth con refresh rotation

Cada refresh emite un nuevo par y revoca el anterior. Si alguien usa un refresh ya canjeado, todos los tokens del usuario se invalidan — heurística simple para detectar robo de token.

##Retos enfrentados

  1. Capturar series rápido sin teclado. Diseñé inputs con steppers + presets de pesos comunes. De 6 taps por set bajé a 2.
  2. Offline en gimnasios con WiFi roto. Service worker + queue de sincronización. La app graba localmente y sincroniza al volver señal.
  3. Gráficas de progreso que no mientan. Hubo que decidir cómo mostrar 'mejor set' vs 'volumen total' — terminé exponiendo ambas con un toggle, en lugar de elegir por el usuario.

##Aprendizajes

  • Construir para vos mismo es el mejor product brief. Cada decisión tiene un usuario real (yo) probando en el gimnasio.
  • NestJS escaló mejor de lo que esperaba para un side-project. La modularización por feature compensa el boilerplate inicial.
  • La parte difícil de un tracker no es guardar datos — es mostrarlos en el momento justo. Pasé más tiempo en UX de gráficas que en el modelo de datos.
